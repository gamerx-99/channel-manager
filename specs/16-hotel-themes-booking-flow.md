## What a theme may show (data rules)
Only data the hotel actually has:
- The hotel name.
- `hero_copy`, which is the intro, at most about 60 words.
- The address.
- `hotel_media`: a hero image plus up to 8 gallery images, each with its caption.
- Room types: name, capacity, and "from ฿X / night" from `base_price`.
- The booking box.
- A location block: the address, plus a map placeholder or embed with no API key.
- Footer text "Booking powered by hayhost".

NEVER render these, even when the reference shows them:
- A founding year, "since", or family-history text.
- Stats rows.
- Reviews, ratings, stars or awards.
- Amenity icons or lists, or m²/SQM.
- Phone numbers, LINE, WhatsApp or concierge contacts.
- Cancellation, tax or levy text, house rules, or check-in times.
- "Instant confirmation" or "verified in N minutes".
- Bank transfer or wire options (we take PromptPay only).
- Weather widgets or live-rate badges.
- Grayscale or duotone photo filters.
- A mobile bottom nav with Amenities, Concierge, Dining or Room service.

The full strip list per theme is in `.agent/orchestrator-notes.md` under "Stitch themes", and in `design/stitch-prompts/v2/00-shared-rules.md` (the DATA RULES block).

## Fonts
- The Stitch fonts have no Thai glyphs, so every theme pairs its Latin fonts with a Thai font:
  - Serif themes use Noto Serif Thai.
  - Sans themes use Noto Sans Thai or IBM Plex Sans Thai.
- Load fonts per theme (one Google Fonts `<link>` added when the theme mounts), not globally in `index.css`.
- Thai text must never fall back to a system font.

## Styling approach
- The app uses Tailwind v4. The Stitch HTML uses a Tailwind v3 CDN config whose token names (`primary`, `surface`, …) clash with the app.
- So each theme is a set of CSS custom properties scoped under `.theme-<name>`, for example `--t-bg`, `--t-surface`, `--t-text`, `--t-muted`, `--t-primary`, `--t-on-primary`, `--t-font-heading`, `--t-font-body` and `--t-radius`.
- Layout is per-theme components (`client/src/components/hotel-themes/<Name>Landing.tsx`).
- Shared pieces must read only the `--t-*` variables. The shared pieces are the booking flow, the room card data and the footer.
- Do not add theme tokens to the global Tailwind theme.

## Booking flow (owner-defined, 2026-10-28)
Today the wizard has 6 steps: dates+guests, room list (hold), add-ons, guest info (calls `confirmBookingDetails`), summary, PromptPay. Change it to 5 steps:
1. **Dates and room**: the calendar (`BookingDateRangePicker`), adults/children, and the room list on the SAME step.
   - The room list refetches when the dates or guests change.
   - Clicking an available room calls `holdRoomType`, which starts the 15-minute hold.
   - Show "Only N left" only when N ≤ 2. Show the min-stay note when it applies.
2. **Add-ons**: the hotel's services, each with a quantity stepper.
   - Each line shows its unit: per night, per person per night, or once.
   - It shows a running total. Show "Skip" when the hotel has no services.
3. **Guest info**: full name* and phone*.
   - Email and special requests are optional.
   - Guests are shown read-only.
   - Submitting calls `confirmBookingDetails`, as today.
4. **Summary**: hotel, room, dates, nights, guests, guest name, the add-on lines and the total (`confirmBookingDetails` result `amount`), plus "Edit details" and "Proceed to payment".
5. **Payment**: `PaymentQR` as today.

The hold countdown shows on steps 2–5, and the step indicator reads "Step N of 5".

Add-ons in the payload:
- The 13-04a fix makes the server price add-ons by `hotel_service_id`. Send `hotel_service_id` and `quantity` for each selected service.
- If the current Supabase `confirmBookingDetails` input schema does not accept `hotel_service_id` yet, do NOT change the server. Keep the current payload and log it in OPEN_QUESTIONS.
  - The live price flaw is tracked separately and is an owner decision.
