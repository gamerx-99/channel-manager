## 2026-10-26 — iCal sync: one connection = one room; OTA blocks are bookings rows; pg_cron every 15 min
**Decision** (human chose each option in chat):
1. Each `ota_connections` row maps to **one physical room** (`room_id`). Booking.com
   and Airbnb iCal feeds describe a single unit, so a hotel with Booking.com on two
   rooms adds two connections ("Booking.com - 101", "Booking.com - 102").
2. Imported VEVENTs are stored as **`bookings` rows with `source = 'ota_ical'`**
   (price 0, no guests, keyed by `(ota_connection_id, external_uid)`), reconciled
   atomically by the `sync_ota_ical_blocks` RPC. The existing `prevent_double_booking`
   exclusion constraint, the public inventory RPC and the calendar then treat them as
   occupied for free. An event that overlaps an existing booking is not inserted; it is
   returned as a conflict, and the connection status becomes `conflict`.
3. The export feed is `GET /api/ical/<64-hex token>.ics`, served via the token-gated
   `get_ota_ical_export` RPC: date ranges only, never guest data, and never the blocks
   the same connection imported (no echo loop).
4. Scheduled sync is **Supabase pg_cron + pg_net every 15 minutes** calling
   `POST /api/cron/ota-ical-sync` (Bearer `CRON_SECRET`, stored in Vault). The human
   asked about every 1 minute; 15 was kept because OTAs refresh and pull iCal only every
   1-3 hours, so faster polling adds rate-limit risk without fresher data. The cron run
   has no end user, so it is the one OTA path that uses the service-role client.
**Why not a separate blocks table**: every availability query, `holdRoomType` and the DB
exclusion constraint would have had to learn about a second source of occupancy.
**Why not Vercel Cron**: `vercel.json` is banned-zone, and the Hobby plan caps crons
at once a day.
**Status**: closed (implemented 2026-10-26, migration pending human apply).

## 2026-08-30 — Housekeeping: fixed boolean checklist + three-state status (T03-01 recon)
**Decision**: `housekeeping_tasks` checklist is **fixed boolean columns** (small set, default `false`), not `jsonb`. Status is a **`text` column with `CHECK (status IN ('pending','in_progress','done'))`** — three states taken verbatim from `specs/03-housekeeping-board.md` Data model — matching the existing `text + CHECK` pattern used by `bookings.status` and `room_housekeeping_status.status`. Table shape: `id uuid PK`, `room_id uuid FK rooms(id) ON DELETE CASCADE NOT NULL`, `hotel_id uuid FK hotels(id) ON DELETE CASCADE NOT NULL` (denormalised for RLS/scoping without an extra `rooms` join), `booking_id uuid FK bookings(id) ON DELETE SET NULL`, `assigned_to uuid FK auth.users(id) ON DELETE SET NULL`, `due_date date NOT NULL`, `status text NOT NULL DEFAULT 'pending'`, fixed checklist booleans, `created_at/updated_at timestamptz`.
**Why — checklist fixed vs jsonb**: spec `specs/03-housekeeping-board.md:26-28` explicitly says "decide based on how much variability real checklists need; start with a fixed small set unless told otherwise, per the 'safest default' rule". No variability signal exists in the spec — the checklist is described as a "fixed small set". `CLAUDE.md` Hard Rule 7 (safest default, never invent requirements) therefore selects fixed columns. Fixed booleans are queryable without GIN indexes, type-safe under `zod`/`Supabase` row types, and trivially addable later; `jsonb` would add JSON-schema validation, untyped `payload->>` queries, and an unnecessary migration to unroll if a future need for variability appears. The decision is reversible: a later ticket can add a `jsonb` column and migrate booleans into it — the reverse (unrolling `jsonb` into columns) is harder, so starting fixed is the lower-risk direction.
**Why — status enum as text+CHECK not Postgres enum type**: codebase has zero `CREATE TYPE ... AS ENUM` usage — every status in `supabase_migration_production.sql` is `text + CHECK` (`rooms.status` `available/occupied/maintenance`, `bookings.status` `confirmed/checked_in/checked_out/cancelled`, `room_housekeeping_status.status` `clean/dirty/out_of_order`). Reusing that pattern avoids a `DROP TYPE` migration difficulty and keeps RLS predicate text-comparison simple.
**Proposed fixed checklist columns** (T03-02 to finalise names before migration): 5 booleans, all `NOT NULL DEFAULT false` — `bed_made`, `bathroom_cleaned`, `towels_replaced`, `amenities_restocked`, `floor_cleaned`. Small enough to fit a single board cell, covers the typical hotel turnover without inventing domain-specific items (e.g. minibar) the spec never mentions.
**Permission split confirmed**: `shared/authorization.ts` (see evidence) grants `housekeeping.view_room_status` to `super_admin` (blanket), `admin` (read-only), `hotel_owner`, `front_desk`, `housekeeping`; grants `housekeeping.update_room_status` to `super_admin`, `hotel_owner`, `housekeeping` only. Critically, `revenue_manager` currently has **neither** housekeeping permission (rejected spec's parenthetical assumption that it has view — code shows zero `housekeeping.*` in its matrix). Read path (`listHousekeepingTasks`) must therefore gate on `housekeeping.view_room_status` via `is_hotel_member`/`can('housekeeping.view_room_status')`; write path (`createHousekeepingTask`/`updateHousekeepingTaskStatus` + assign) must gate on `housekeeping.update_room_status` which maps to `can_manage_housekeeping(hotel_id)` (`super_admin` or `hotel_owner` or `housekeeping` per `supabase_migration_production.sql:683-693`). Reuse `DashboardCalendarView` precedent (`Home.tsx:canEditCalendar = super_admin/hotel_owner/revenue_manager` view-vs-edit split) but adapted: for housekeeping board, `front_desk` and `revenue_manager` are view-only (if the latter is later granted view), `hotel_owner`/`housekeeping` can edit/assign — matching spec Business rules "Editing follows the same view-vs-edit role split already established in DashboardCalendarView". No new `Permission` string needed.
**Alternatives considered**: `checklist jsonb` with `{ items: [{key, done}] }` (rejected — over-engineering per spec's own "safest default" rule, harder to index/filter, needs JSON schema); Postgres native `CREATE TYPE housekeeping_status AS ENUM` (rejected — no precedent in this codebase, harder to evolve); reusing `room_housekeeping_status` table instead of a new `housekeeping_tasks` table (rejected — that table is a single `room_id PK` current-condition row `clean/dirty/out_of_order`, not a per-day assignable task with due_date/assignee/booking linkage).
**Status**: open — recon only, no production code touched. Implementation follows in T03-02 (migration + RLS) and T03-03 (tRPC validation). See `.agent/recon/REPORT.md` 2026-08-30 T03-01 section for full code evidence.

## 2026-08-30 — MFA: blocking enforcement for super_admin/admin (T09-01 recon)
**Decision**: `super_admin` and `admin` (platform roles per `shared/authorization.ts` `PLATFORM_ROLES`) must have TOTP MFA enrolled before any authenticated access is granted — **blocking at first login**, not a grace-period nag. Hotel-level roles (`hotel_owner`, `revenue_manager`, `front_desk`, `housekeeping`) are opt-in only in this phase; required step-up MFA for SlipOK settings (Phase 01 tie-in) will prompt enrollment at point of use rather than silently deny.
**Why — blocking vs grace-period**: spec `specs/09-authenticator-mfa.md` explicitly prefers blocking ("blocking is safer and simpler, prefer it unless told otherwise"). Recon confirms grace-period adds non-trivial state: expiry tracking, nag UI, bypass window, and audit surface for the two most privileged roles. Blocking keeps the auth gate stateless (Supabase Auth factor state is the source of truth) and matches the product's trust model where `super_admin` already bypasses most hotel-scoped RLS — MFA is the only compensating control for that breadth.
**Why — Supabase API supports blocking without custom storage**: verified against installed `supabase-js@2.112.3` bundle (`node_modules/@supabase/supabase-js/dist/umd/supabase.js`, GoTrueClient). Client API is `supabase.auth.mfa.*` (wrap of `GoTrueClient.mfa`): `enroll({ factorType:'totp', friendlyName, issuer })` → `challenge({ factorId })` → `verify({ factorId, challengeId, code })` / `challengeAndVerify({ factorId, code })`, plus `unenroll({ factorId })`, `listFactors() → { all, totp, phone, webauthn }`, `getAuthenticatorAssuranceLevel() → { currentLevel, nextLevel, currentAuthenticationMethods }` (reads JWT `aal`/`amr` claims, elevates `nextLevel` to `aal2` when verified factors exist; emits `MFA_CHALLENGE_VERIFIED`). No new table expected — factor state lives in Supabase Auth — so blocking can be enforced purely by checking `listFactors`/`getAuthenticatorAssuranceLevel` post-login before allowing navigation. No app-side "verified within N minutes" table needed unless Supabase's session AAL proves insufficient for SlipOK step-up freshness.
**Current auth flow gap**: `client/src/pages/Login.tsx` calls `supabase.auth.signInWithPassword` and navigates to `/dashboard` unconditionally — no post-login MFA factor check, no `getAuthenticatorAssuranceLevel` call, no challenge UI. `client/src/_core/hooks/useAuth.ts` tracks `supabase.auth.getSession()` / `onAuthStateChange` only (`user`, `loading`, `isAuthenticated`), with no AAL awareness. `client/src/App.tsx` `PrivateRoute` gates on `useAuth` + `trpc.auth.me` / `routeScope` permissions only. Any blocking enforcement will need: (a) post-login branch in `Login.tsx` that calls `mfa.listFactors()` + `mfa.getAuthenticatorAssuranceLevel()` for platform roles and redirects to enroll/verify when `currentLevel !== 'aal2'`, (b) a session-level guard (or `requireRecentMfaVerification()` helper per spec) for SlipOK step-up that checks AAL freshness rather than just enrollment, with `hotel_owner` enrollment prompt (not silent block) when no factor exists.
**Alternatives considered**: grace-period nag (rejected — adds temporal state and leaves privileged sessions under-protected during window); SMS/email MFA (out of scope — spec restricts to TOTP per human request).
**Status**: open — recon only, no production code touched. Implementation follows in 09 tickets. See `.agent/recon/REPORT.md` 2026-08-30 T09-01 section for full code evidence.

## 2026-08-29 — Financials: withhold from super_admin by design
**Decision**: `property.view_financials` is granted to `hotel_owner` only — not
`revenue_manager`, not `admin`, and explicitly excluded from `super_admin`'s normal
blanket permission grant (`shared/authorization.ts`). The `financials` tRPC
procedure uses `requirePermission`, not `requireHotelPermission`, because the latter
unconditionally bypasses for `super_admin` regardless of the permission matrix.
**Why**: hotel revenue is the property's own business data — the platform operator
seeing it by default isn't part of this product's trust model, even though
`super_admin` normally sees everything else. This is a deliberate, unusual carve-out
from this codebase's dominant "super_admin can do everything" convention — noted
explicitly in code comments so a future maintainer doesn't "fix" it as a bug.
**Status**: closed.

## 2026-08-30 — Signup links: hotel-first, single-use
**Decision**: A super_admin creates the hotel first (existing flow, unchanged), then
generates a signup link scoped to that specific hotel. The link never creates a
hotel itself — only self-service account creation + `hotel_owner` role binding. Each
link is single-use, enforced atomically (`update ... where used_at is null and
expires_at > now()`), and duration is admin-settable in hours (not fixed presets).
**Why**: keeps hotel creation entirely behind `super_admin` auth (unchanged trust
boundary) while removing the need for an admin to know a new owner's email in
advance. Single-use avoids one link being shared across multiple prospective owners
for the same hotel, which the 1-hotel-owner-per-hotel rule wouldn't allow anyway.
**Status**: closed.

## 2026-08-29 — Vercel: bundle the server, don't let Vercel's builder resolve it
**Decision**: `api/index.ts` imports the pre-bundled `dist/index.js` (produced by
this repo's existing `esbuild --bundle --splitting` step), not
`server/_core/index.ts` source directly.
**Why**: Vercel's zero-config TypeScript builder compiles `api/` files individually
rather than bundling the whole import graph. Under ESM (`"type": "module"`), that
left every extensionless relative import — including every `@shared/*` alias in the
server tree — unresolved at runtime (`ERR_MODULE_NOT_FOUND`), even though the same
code worked fine locally where Node resolves modules differently. Pointing at the
already-correctly-bundled single-file output sidesteps Vercel's resolver entirely.
A second, related issue (rollup/vite native binary crash on cold start) was fixed by
making the `./vite` import inside `server/_core/index.ts` a dynamic import and adding
`--splitting` to the esbuild step, so that dev-only code path — never invoked on
Vercel — is never even loaded there.
**Status**: closed.
